## 1. 공통 컴포넌트 (모든 기준정보 화면에 적용)

### 1-1. version 숨김 + 최종 변경 표시
- 화면에 표시되는 `조회 vN` 텍스트를 모든 기준정보 화면에서 제거한다. version은 내부 낙관적 잠금용으로만 쓴다.
- 그 자리(카드 하단 왼쪽, 저장 버튼 맞은편)에 `최종 변경 {변경자명} · {YYYY-MM-DD HH:mm} · 이력 보기`를 표시한다.
- 저장 시 화면을 연 시점의 version과 현재 version이 다르면 저장을 막고 "다른 사용자가 먼저 수정했습니다. 최신 내용을 불러옵니다."를 안내한 뒤 최신 데이터를 다시 불러온다.
- 변경 사항이 없으면 저장 버튼은 비활성이다 (현재 동작 유지).

### 1-2. 변경 이력 드로어
- 폼 안에 있는 "변경 이력" 영역을 제거하고, `이력 보기` 링크를 누르면 **우측 슬라이드 드로어**로 이력을 보여 준다.
- 드로어 항목: 변경 일시, 변경자, 구분(등록/수정), 변경 필드(이전 값 → 새 값).
- 공통 컴포넌트로 만들어 모든 기준정보 화면(사용자·역할 우측 상세 포함)에 같은 패턴으로 적용한다.
- 시드 데이터에도 `시스템 · 등록` 이력을 생성한다 (현재 회사 정보는 "이력이 없습니다"로 나옴).

### 1-3. 주소 입력 (카카오(다음) 우편번호 서비스)
- 카카오(다음) 우편번호 서비스를 사용한다. API 키가 필요 없다.
  - 스크립트: `https://t1.daumcdn.net/mapjsapi/bundle/postcode/prod/postcode.v2.js` (Next.js라면 `next/script`로 필요한 화면에서만 로드)
- 입력 구성: `[우편번호(읽기 전용)] [주소 검색 버튼]` / `기본주소(읽기 전용)` / `상세주소(직접 입력)`
- 검색 결과 매핑: `zonecode` → 우편번호, `roadAddress` → 기본주소 (사용자가 지번을 선택하면 `jibunAddress`), `buildingName`이 있으면 기본주소 뒤에 `(건물명)` 참고 항목으로 붙인다.
- 주소 선택 후 상세주소 입력칸으로 포커스를 이동한다.
- 공통 컴포넌트로 만들어 회사 정보와 센터 관리에서 같이 쓴다.

### 1-4. 입력 검증 공통 규칙
- 오류 문구는 필드 바로 아래에 빨간 글씨로 표시한다.
- 저장 시 오류가 있으면 첫 번째 오류 필드로 포커스를 이동한다.
- 서버(API)에서도 같은 규칙으로 한 번 더 검증한다.

| 필드 | 규칙 | 오류 문구 |
|---|---|---|
| 사업자등록번호 | 숫자 10자리, 입력 중 하이픈 자동(3-2-5), placeholder `000-00-00000`, 체크섬 검증(아래) | 올바른 사업자등록번호가 아닙니다 |
| 전화번호 | 숫자 9~11자리 또는 대표번호(15xx·16xx·18xx, 8자리), 입력 중 하이픈 자동 | 전화번호 형식을 확인하세요 |
| 이메일 | 이메일 형식 | 이메일 형식을 확인하세요 |
| 주소 | 우편번호·기본주소는 검색으로만 입력, 상세주소 필수 | 주소를 검색해 선택하세요 / 상세주소를 입력하세요 |

사업자등록번호 체크섬:
```
가중치 = [1,3,7,1,3,7,1,3,5]
sum = Σ(d[i] * 가중치[i]) for i=0..8  +  floor(d[8] * 5 / 10)
유효 = ((10 - sum % 10) % 10) == d[9]
```
- 기존 회사 정보 화면의 입력칸 아래 회색 안내 문구 `000-00-00000`은 제거하고 placeholder로 옮긴다.

## 2. 회사 정보 화면 수정 (/master/company)

### 2-1. 구성
- 화면에서 **센터 카드를 제거**한다 (센터는 3번의 별도 메뉴로 이동).
- 회사 정보는 "우리 회사" 1건을 수정하는 **단건 폼**을 유지한다.
- 우측 열은 비워 둔다. 나중에 "입고확인서 머리글 미리보기"가 들어갈 자리이며 **이번 작업 범위가 아니다** (입고확인서 범위 추가가 아직 미확정).

### 2-2. 필드

| 필드 | 필수 | 규칙 |
|---|---|---|
| 회사명 | 필수 | 1~50자, 앞뒤 공백 제거 |
| 사업자등록번호 | **필수** | 1-4 규칙 |
| 대표자명 | **필수** | 1~20자 |
| 주소 | **필수** | 1-3 주소 컴포넌트 (우편번호·기본주소·상세주소) |
| 대표 전화 | 선택 | 1-4 규칙 |
| 이메일 | 선택 | 1-4 규칙 |

### 2-3. DB
- 회사 테이블의 주소를 `zip_code`, `addr1`(기본주소), `addr2`(상세주소)로 분리한다.
- 사업자번호·대표자명·주소를 NOT NULL로 바꾼다 (시드를 먼저 채운 뒤 적용).
- 이력 테이블(_HIS)도 같은 컬럼 구조로 맞춘다.

### 2-4. 시드 (가상 데이터)
- 회사명: `온길로지스(주)` (기존 "로지링크"에서 변경. 시스템명 LogiLink와 3PL 운영사명을 분리하기 위함. 사이드바 제품 로고 "LogiLink"는 그대로 유지)
- 사업자등록번호: 체크섬을 통과하는 가상 번호 (예: `123-45-67891`)
- 대표자명·주소·전화·이메일: 가상 값으로 채운다

### 2-5. 화면 규칙 패널(?) 문구 수정
- "출력물 머리글" 항목: 기존 "상차확인서(거래명세서 역할, D13) 등 출력물 머리글에 씁니다" → **"3PL이 발행하는 출력물의 머리글에 씁니다. 대상 출력물은 확정 후 반영합니다."**
  (상차확인서는 화주사가 발행하는 문서라 3PL 회사 정보가 들어가지 않음)
- "센터 정보" 항목 삭제 → "센터는 기준정보 > 센터 메뉴에서 관리합니다."로 교체
- "동시 수정 방지" 항목 유지
- "수정 권한: 3PL 관리자만 수정할 수 있습니다. 3PL 운영담당은 조회만 할 수 있습니다." 추가

## 3. 센터 관리 메뉴 신설 (/master/centers)

### 3-1. 메뉴
- 사이드바 기준정보에서 **회사 정보 바로 아래에 "센터"** 메뉴를 추가한다.
- 화면 패턴은 사용자·역할 화면과 같은 **목록 + 우측 상세**로 만든다. 센터가 1건이어도 목록에 1행으로 나온다.
- 상단에 필터(사용 여부), 총 건수, `+ 등록` 버튼을 둔다.

### 3-2. 목록 컬럼
센터 코드 / 센터명 / 주소(기본주소) / 입고 문의 전화 / 센터 담당자 / 일마감 예정 시각 / 최종 변경 / 사용 여부

### 3-3. 상세 필드

| 필드 | 필수 | 규칙 |
|---|---|---|
| 센터 코드 | 필수 | 영문 대문자+숫자 3~5자, 중복 불가, **등록 후 수정 불가**(읽기 전용) / "이미 사용 중인 센터 코드입니다" |
| 센터명 | 필수 | 중복 불가 / "이미 등록된 센터명입니다" |
| 주소 | 필수 | 1-3 주소 컴포넌트 |
| 입고 문의 전화 | 필수 | 1-4 전화 규칙 |
| 센터 담당자 | 선택 | 3PL 소속 사용자 중에서 선택 |
| 일마감 예정 시각 | 필수 | 24시간 HH:mm |
| 사용 여부 | 필수 | 사용/사용 안 함. **삭제 기능은 두지 않는다** (과거 전표가 참조하므로 비활성 처리) |

- "사용 안 함"으로 바꿀 때 그 센터에 소속된 사용 중인 사용자가 있으면 "소속 사용자 N명이 있습니다"라고 경고한 뒤 확인을 받는다.
- 우측 상세 하단에도 1-1(최종 변경 · 이력 보기)과 1-2(이력 드로어)를 적용한다.

### 3-4. DB
- 센터 테이블: `center_cd`(PK 또는 UK), `company_id`(회사 FK), `center_nm`, `zip_code`, `addr1`, `addr2`, `inbound_tel`, `manager_user_id`(NULL 허용, 사용자 FK), `daily_close_time`, `use_yn`, `version`, 공통 감사 컬럼
- 센터 이력 테이블(_HIS)을 추가한다.
- 회사 : 센터 = 1 : N. 지금은 회사 1건, 센터 1건(용인1센터, 코드 YI1)이지만 N개를 전제로 설계한다.
- 기존 회사 정보 화면에 있던 센터 데이터를 이 테이블로 이관한다.

### 3-5. 일마감 예정 시각 이동
- 운영 설정의 `DAILY_CLOSE_TIME`을 **센터 테이블의 `daily_close_time`으로 이동**하고, 운영 설정 목록에서는 삭제한다.
- 기준: 센터마다 다른 값은 센터 관리, 회사 전체 정책은 운영 설정. (미종결 알림 기준 경과일은 운영 설정에 그대로 둔다)
- 기존 설명 문구("마감 실행 이후 확정된 검수 실적은 다음 날 실적으로 귀속합니다")는 센터 상세의 필드 도움말로 옮긴다.
- 이 값을 참조하는 코드가 있다면 센터 기준으로 읽도록 바꾼다.

### 3-6. 화면 규칙 패널(?)
- 센터는 N개를 관리하며, 각 센터는 회사(3PL 운영 법인) 1곳에 속한다.
- 센터 코드는 등록 후 바꿀 수 없다.
- 센터는 삭제하지 않고 "사용 안 함"으로 처리한다.
- 센터마다 다른 값(입고 문의 전화, 일마감 예정 시각)은 센터에서, 회사 전체 정책은 운영 설정에서 관리한다.
- 수정 권한: 3PL 관리자만.

## 4. 3PL 관리자 역할 추가

### 4-1. 역할
- 역할 코드에 **"3PL 관리자 (Web)"**를 추가한다. 사용자·역할 화면의 역할 필터와 등록 드롭다운에도 반영한다.
- 기존 역할: 3PL 운영담당(Web), 3PL 입고검수자(PDA), 화주사 담당자(Web), 화주사 상차담당(PDA)

### 4-2. 권한 (이번 작업 범위)

| 화면 | 3PL 관리자 | 3PL 운영담당 | 화주사 |
|---|---|---|---|
| 회사 정보 | 조회·수정 | 조회만 (입력칸 읽기 전용, 저장 버튼 숨김) | 메뉴 비노출 |
| 센터 | 조회·등록·수정 | 조회만 | 메뉴 비노출 |
| 그 외 업무 화면 | 3PL 운영담당 권한 전체 포함 | 기존 유지 | 기존 유지 |

- 화면 숨김뿐 아니라 **API에서도 권한을 검증**한다.
- 나머지 기준정보 메뉴(화주사, 품목, 품목 등록 요청, 사유 코드, 사용자·역할, 휴무일, 운영 설정)의 역할별 권한은 **바로 적용하지 말고, 현재 코드 기준으로 권한 매트릭스 초안을 표로 제안해줘.** 내가 정한 뒤 반영한다.

### 4-3. 시드
- 3PL 관리자 사용자 1명을 추가한다 (예: 아이디 `han.soyul`, 이름 `한소율`, 소속 용인1센터).
- 로컬에서 역할별로 화면을 확인할 수 있게 사용자 전환 방법을 알려줘 (이미 있으면 그 방법을 안내).
