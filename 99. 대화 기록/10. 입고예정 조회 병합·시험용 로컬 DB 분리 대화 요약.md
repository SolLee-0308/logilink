# 입고예정 조회 병합·시험용 로컬 DB 분리 대화 요약

## 1. 요약

Sol이 입고예정 조회 화면을 확인했고, **경과일 기준은 현재 구현(입고예정일 기준 강조 + 승인 후 일수 보조 표시)을 유지**하기로 확정했다. 코드 변경 없이 `feat/plan-inquiry`를 `main`에 병합하고 push했다(병합 커밋 `62a3cc1`).

이어서 시험 환경을 점검한 결과, **개발 서버와 점검 스크립트가 모두 운영 DB(Supabase)에 연결되어 있어 안전한 시험 환경이 없다**는 점을 확인했다. Supabase 무료 플랜은 프로젝트 2개가 한도인데 수업용 1개·로지링크 1개로 이미 가득 차 있어, **Prisma에 포함된 `prisma dev`로 PC 안에 로컬 DB를 띄워 시험용으로 분리**하기로 했다.

## 4. 결정 사항: 시험용 로컬 DB 분리

**결정:** Supabase 프로젝트를 새로 만들지 않고, `prisma dev`로 PC 안에 로컬 DB를 띄워 시험용으로 쓴다. 별도 설치·비용이 없다.

| 단계 | 내용 | 기존 파일 영향 |
| --- | --- | --- |
| 1 | 로컬 DB 실행(`prisma dev`) | 없음 |
| 2 | 시험용 연결 정보 파일 `.env.test` 생성 | 없음(새 파일, git 제외) |
| 3 | 로컬 DB에 테이블 생성 + 기초 데이터(seed) 입력 | 없음 |
| 4 | `package.json`에 시험용 명령 추가: `npm run dev:test`, `npm run db:test:reset`, `npm run check:test` | `package.json` 수정(명령 추가, Sol 승인) |

**구축 결과**

| 항목 | 내용 |
| --- | --- |
| 로컬 DB | `prisma dev --name logilink-test`, 포트 51214. 이전에 만든 `logilink-test2`·`logilink-test3`(정지 상태)는 손대지 않음 |
| 연결 파일 | `03. 개발/.env.testdb` — DB 주소 2개만 담고, 나머지 값(AUTH_SECRET 등)은 `.env`에서 읽음. git 제외 |
| 실행 도구 | `scripts/with-test-db.mjs` — `.env.testdb` 주소를 넣고 명령 실행. **주소가 localhost가 아니면 실행을 멈춤**(운영 DB 오접속 방지) |
| 테이블·데이터 | 마이그레이션 14개 적용 확인, seed 입력(화주사 5, 품목 14, 사용자 13, 입고예정 13, ASN 6, 상차 실적 3 등) |
| 검증 | `check-inquiry-rules.ts`를 로컬 DB로 실행해 27건 모두 통과(승인 건 취소도 로컬에서만 실행됨). 시험 서버 `http://localhost:3001` 응답 확인 |

**사용 구분**

| 명령 | 연결 DB | 용도 |
| --- | --- | --- |
| `npm run dev` | 운영 DB(Supabase), 3000 포트 | 실제 확인용. 데이터를 바꾸는 기능은 누르지 않는다 |
| `npm run dev:test` | 로컬 시험 DB, 3001 포트 | 승인 건 취소 등 데이터를 바꾸는 기능 시험. 두 서버를 함께 띄울 수 있다 |
| `npm run db:test:reset` | 로컬 시험 DB | 로컬 DB를 비우고 seed로 다시 채운다 |
| `npm run check:test -- scripts/check-○○-rules.ts` | 로컬 시험 DB | 점검 스크립트 실행. 이제 운영 DB에 돌리고 seed로 되돌릴 필요가 없다 |

**PC를 다시 켰을 때:** 로컬 DB가 꺼져 있으면 `npx prisma dev --name logilink-test --detach`로 먼저 켠다(데이터는 남아 있다).

**검수 중 발견·수정(동시 연결 오류):** 시험 서버의 품목 관리·품목 등록 요청 화면에서 `Connection terminated unexpectedly` 오류가 났다. 로컬 DB(`prisma dev`)가 한 프로그램에서 여러 연결로 동시에 조회하면 연결을 끊기 때문이다(연결 5개: 30회 중 30회 실패, 1개: 30회 모두 성공). 운영 DB에는 해당 없다. `src/server/db.ts`의 연결 수를 `DB_POOL_MAX` 값으로 바꿀 수 있게 하고(없으면 기존과 같은 5), `.env.testdb`에만 `DB_POOL_MAX="1"`을 넣었다. 오류가 반복되면서 로컬 DB가 모든 연결을 끊는 상태가 되어 로컬 DB를 다시 켰다(데이터 유지).

**로컬 DB가 응답하지 않을 때:** `npx prisma dev stop logilink-test` → `npx prisma dev start logilink-test`.

**참고:** `prisma migrate reset`은 AI(Claude Code)가 실행하면 Prisma 안전장치가 막는다. 이번 초기 구축은 데이터를 지우지 않는 `migrate deploy` + seed로 진행했다. `db:test:reset`은 Sol이 직접 실행하면 된다.

**유의 사항:** 로컬 DB는 seed 기초 데이터로 시작하므로 운영 DB에 쌓인 실제 데이터는 없다. 시험 데이터가 필요하면 seed나 기존 점검 스크립트(`dev-shipper-edit.ts` 등)로 만든다.

**점검:** 타입 검사 통과, 단위 테스트 51건 통과, 시험 서버(3001) 브라우저 점검 통과(2차 반영 후 22건: 접은 상세 → 목록 오른쪽 끝까지, 구분선, 메뉴 접기 버튼 위치 추가)(메뉴 접기·쿠키 유지, 상세 접기·펼치기, 스크롤 후 조회조건 바 위치, 화주사 찾기 선택, 돌아가기 버튼·경로 한 줄, 기준정보·입고 계획 주요 화면 열림), 브라우저 오류 없음.

## 6. 품목코드 채번·엑셀 일괄 요청 (2026-11-06)

## 10. 입고검수(PDA) 화면 정리 (2026-11-06)

Sol이 입고검수 화면을 만들었는지 물음 → PDA 입고검수(시작·작업·검수 내역·대시보드)는 11-05에 만들어 main에 병합, 웹 '입고검수 실적'·'잔량 종결·일마감' 메뉴는 4단계로 미뤄 아직 없음(검수 결과는 ASN·상차 현황/상차 실적 상세 안에 표시)이라고 답함.

| No | Sol 제기 | 결과 |
| --- | --- | --- |
| 1 | 상차 작업과 일관된 화면 구성 | 상태 한 줄 머리, 스캔 영역 너비 끝까지 연보라, 품목 줄 목록 + 상태 색 글자, 내 입력 접힌 줄, 전체 진행 막대 없앰 |
