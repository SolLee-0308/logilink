## 3. main 병합·push

### 3-1. 병합 전 결정 사항 점검

병합 자체는 막히는 것이 없었다. main이 원격과 같았고, 브랜치는 main 위에 커밋 4개만 얹은 상태였다(c52fd5e 입차 개발, c63131d 화면 검수 피드백, 86bcfc6 정의서 v1.8, 5c22443 대시보드). 대신 아래 두 가지는 Sol이 정해야 한다고 보고했다.

| 결정 | 내용 | Sol |
| --- | --- | --- |
| ① 운영 DB 마이그레이션 시점 | 20261114 3개(arrival, arrival_backfill, rcv_void_check). backfill은 기존 데이터를 바꾸고, '일마감 처리(시스템)' 출차 시각을 실행 시각으로 찍어서 되돌리기 어렵다. Claude 권고는 병합 직후 적용 | **추후 다시 알려 달라** |
| ② 시연 사이트 반영 시점 | 시연 DB 마이그레이션과 deploy 브랜치 갱신이 필요하다. 반영하면 입차·출차 구분이 화면에 나오므로 시나리오 문서도 고쳐야 한다. 대시보드 '준비 중'은 코드에서 막고 있어 유지된다 | **추후 다시 알려 달라**(선생님이 금요일까지 시연 테스트를 하지 않을 예정) |

### 3-2. 병합 실행

Sol 지시로 main을 fast-forward 병합하고 push했다(`dfa40c2..5c22443`). 시연 사이트는 `deploy` 브랜치만 보므로 영향이 없다.

- **주의:** 운영 DB에는 아직 마이그레이션을 하지 않았다. 그래서 `npm run dev`(운영 DB)로 띄우면 새 컬럼 때문에 오류가 날 수 있다. 그때까지는 시험 DB(`dev:test`)로 작업한다.
- 병합분에 `00. 기본/01. 한빛식품 품목 정보.md` 삭제가 포함돼 있다. c52fd5e에서 의도하고 지운 것이다(대화 기록 22에 기록됨).

## 4. 개발 진행 상태와 남은 일 정리

Sol이 "개발이 마무리됐느냐"고 물었다. **기능 개발은 끝났고, 지금은 마무리 정리 단계**라고 답했다. 마지막 메뉴였던 대시보드까지 main에 들어갔다. 남은 일은 배포 마무리(운영 마이그레이션·시연 반영), 마무리 때 정하기로 한 과제, 대화 기록 23에서 넘어온 일이다.

## 5. 시연 사이트 관련 결정

| 항목 | Sol 결정 |
| --- | --- |
| API 키(AI 판독·공휴일) | **시연 사이트에는 넣지 않음** |
| 시연 사이트 폐쇄 | **11-22(일) 또는 11-23(월) 무렵 폐쇄 예정** |

키가 없을 때 시연 사이트의 동작은 이렇다. AI 판독은 그 화주사 품목으로 만든 '예시 판독'을 돌려준다. 공휴일 불러오기는 "서비스 키가 없습니다 … .env에 넣어 주세요" 오류 문구가 뜬다.

## 6. 챗봇 (새 범위)

Sol이 사용자 편의를 위해 챗봇을 넣고 싶다고 했다. 정의서와 요청서에 없는 새 범위라서 방향부터 정했다.

| 항목 | Sol 결정 |
| --- | --- |
| 역할 | **사용법 안내만**(메뉴 위치, 처리 순서, 상태 뜻, 오류 문구 뜻). DB 조회와 처리 대행은 하지 않음 |
| 위치 | **3PL·화주사 웹 화면만**(오른쪽 아래 버튼 → 대화 창). PDA 제외 |
| 순서 | **마무리 과제를 끝낸 뒤** 착수 |

처리 대행은 '상세를 직접 보고 단건 처리' 원칙과 부딪친다. 데이터 조회는 화주사 데이터 범위 위험이 있다. 그래서 둘 다 제외했다. 착수할 때 기획과 시안부터 보여 드리고 확인을 받는다.

## 7. EA 기준 문제 → 품목 입수

### 7-1. 문제

수량은 품목의 '기준 단위'로 센다. 그런데 시험 품목 44개 중 **18개가 기준 단위 BOX이고 EA 환산이 없었다.** 그래서 상자가 터져 낱개로 들어오거나 낱개로 출고해야 할 때 시스템이 수량을 나눌 수 없었다(EA 기준 26개 중 BOX 환산이 있는 것은 5개).

### 7-2. 업계 관행 설명

물류센터는 보통 **"가장 작은 관리 단위(보통 EA)를 기준으로 하고, 입수(BOX 1개에 든 EA 수)는 항상 받아 둔다."** 이커머스와 소매 배송센터는 EA 기준, 박스째 거래하는 B2B는 BOX 기준도 흔하다. 다만 BOX 기준인 곳도 입수는 품목 마스터에 받아 둔다.

### 7-3. Sol 결정

| 항목 | 결정 |
| --- | --- |
| 입수 | 업계 관행대로 품목 마스터에 받는다. **BOX 기준 품목에 입수 칸 추가, 필수** |
| 적용 범위 | **등록 경로 전부**(등록·수정, 요청 등록, 엑셀 일괄)와 목록·상세·엑셀 다운로드 |
| ① BOX 확인 창 | **띄운다** |
| ② PDA 표시 | **현행 "10 BOX 5 EA" 유지**. 11-07 제안("120 EA (= 10 BOX)") 뒤로 PDA가 이미 지시 단위 기준의 박스+낱개 표시로 바뀌어 있었고, 작업자가 실물을 세는 순서와 맞다 |
| ③ 기존 BOX 품목 18개 | 시험 DB를 비워서 해소(8장) |

### 7-4. 구현 (`feat/1117-item-inner-qty` 6687598)

| 구분 | 내용 |
| --- | --- |
| DB | `tb_item.inner_qty` 추가(마이그레이션 `20261117000000_item_inner_qty`). BOX 기준일 때만 2~100000을 허용하는 CHECK를 둠. 칼럼만 추가하고 기존 데이터는 바꾸지 않음 |
| 규칙 | `src/domain/master.ts` — `innerQtyOf`(EA 기준은 BOX 환산, BOX 기준은 저장값), `innerQtyError`(BOX 기준 필수·범위), `needsInnerQty` |
| 품목 등록·수정 | 기준 단위가 BOX면 "1 BOX = [ ] EA" 입수 칸(필수). 입수는 참고 정보이고 수량 계산에는 쓰지 않음 |
| 품목 등록 요청 처리(3PL) | 단위가 BOX면 등록할 때 입수 입력 |
| 엑셀 일괄 등록 | 기존 'BOX입수' 열 재사용. 기준단위가 BOX면 필수이고 입수로 저장 |
| 품목 목록·상세 | '입수' 열 추가(비어 있으면 '미입력' 꼬리표), 상세에 "BOX 1개 = n EA" |
| 엑셀 다운로드 | BOX 기준 품목도 'BOX입수' 열에 입수 표시 |
| 변경 이력 | 입수 변경을 기록 |
| BOX 확인 창 | `BoxBaseConfirm` — "낱개 출고가 없는 품목이 맞나요?" 품목 폼에서 BOX로 바꿀 때, 요청 처리에서 BOX로 [등록]할 때 뜸. 엑셀 일괄 등록은 제외(BOX입수 필수로 대신함) |
| 시험 | `src/domain/inner-qty.test.ts` 4개 추가 → 91/91 |

### 7-5. 점검 (3001)

| 점검 | 결과 |
| --- | --- |
| 목록 '입수' 열·BOX 품목 '미입력' 표시(17건) | 통과 |
| 수정 폼 입수 칸, 비우면 저장 안 됨 | 통과 |
| 입수 6 저장 후 상세 "BOX 1개 = 6 EA" | 통과 |
| 등록 폼: BOX일 때만 입수 칸 | 통과 |
| BOX 확인 창: 뜸 / 취소하면 EA 유지 / 확인하면 BOX·입수 칸 / PLT는 창 없음 | 통과 |

점검 중에 찾아서 고친 문제가 세 가지 있다. 입수 칸에 숫자가 입력되지 않던 문제(정규식 오류), 입수 칸이 너무 넓게 그려지던 문제, 서버가 새 칼럼을 읽기 전에 목록 화면이 멈추던 문제(빈 값 처리 보강, 서버 재시작)다. 품목 등록 요청 처리 화면과 엑셀 일괄 등록은 브라우저로 직접 눌러 보지 않았다. 엑셀은 단위 시험으로, 요청 처리는 타입 검사로만 확인했다.

## 8. 시험 DB 비우기

Sol이 처음부터 테스트하려고 **시험 DB만**, **화주사까지** 비우기로 정했다.

| 구분 | 내용 |
| --- | --- |
| 지운 것 | 품목 44, 품목 등록 요청, 입고예정 90, ASN 88, 상차, 검수, 일마감, 변경 이력, 로그인 기록, 화주사 8, 화주사 담당자 계정 11 |
| 남긴 것 | 회사, 센터 3, 3PL 계정 7(han.soyul 등), 공통·사유 코드, 운영 설정, 휴무일 |
| 방식 | 업무 테이블은 번호를 1부터 다시 매기도록 비우고(TRUNCATE, CASCADE 없이), 화주사 계정의 세션과 계정, 화주사를 차례로 삭제. 하나의 트랜잭션으로 실행 |
| 백업 | 지우기 전에 시험 DB 전체를 세션 임시 폴더 `testdb-backup-20261117.json`에 저장(임시 폴더라 나중에 비워질 수 있음) |
| 확인 | 비운 DB로 3PL 로그인 정상 |

테스트는 **화주사 등록 → 화주사 담당자 계정 만들기 → 품목 등록 → 입고예정 …** 순서로 처음부터 진행한다. 기본 시드(`prisma/seed.ts`)의 BOX 품목에는 아직 입수가 없다. 지금은 시드를 다시 넣을 계획이 없어서 그대로 두었다.
