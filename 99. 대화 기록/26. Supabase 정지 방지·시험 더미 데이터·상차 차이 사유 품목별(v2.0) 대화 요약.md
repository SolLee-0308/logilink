# Supabase 정지 방지·시험 더미 데이터·상차 차이 사유 품목별(v2.0) 대화 요약

## 0. 한눈에 보기

대화 기록 25에 이어서 진행했다. Supabase 일시 정지 메일을 받아 **GitHub Actions로 사흘마다 DB를 조회**하게 했다. 비운 시험 DB에는 Sol이 준 **더미 화주사·품목·사용자**를 넣었다. Sol이 상차 화면을 시험하다가 "부족과 초과가 한 차량에 섞이면 사유 하나로는 안 된다"고 지적해서, 상차 차이 사유를 **차량당 1개에서 품목별 선택으로** 바꾸기로 했다(A안). 정의서 **v2.0 초안**을 새 파일로 쓰고 개발까지 했다. 입고검수 PDA에는 상차 차이 사유를 **참고로 표시**한다.

| 구분 | 결과 |
| --- | --- |
| Supabase 정지 방지 | `.github/workflows/supabase-keepalive.yml` main **a753e69** push, 운영·시연 수동 실행 성공 |
| 시연 사이트 | **폐쇄 취소, 계속 운영**(대화 기록 25의 11-22~23 폐쇄 예정 취소) |
| 시험 DB 더미 데이터 | 화주사 7, 품목 100, 화주사 사용자 19 (시험 DB에만) |
| 상차 차이 사유 품목별 | 정의서 v2.0 초안 + 개발, 브랜치 `feat/1119-load-diff-line` **미커밋** |
| 마이그레이션 | `20261119000000_load_line_diff_reason` **시험 DB에만** 적용 |
| 확인 | 타입 검사 통과, 단위 시험 95/95. 화면 흐름은 Sol이 시험 중 |

**다음 시작 시 할 일:** Sol의 상차·검수 화면 시험 결과를 받아 고친다. 정의서 v2.0 초안과 미결 O6(L06·L07 이름·적용 상태)을 확인받는다. 운영·시연 DB 마이그레이션 시점(미적용 4개 + 20261119 1개)과 시연 반영 시점을 다시 묻는다.

## 1. 시작 전 환경

- 시험 DB(`npx prisma dev --name logilink-test`)를 켜는 중에 샌드박스 권한 오류와 임시 폴더의 pglite.wasm 손상이 있었다. Sol 허락을 받아 Temp의 `@prisma` 폴더를 지우고 샌드박스 밖에서 다시 켰다.
- `npx prisma`를 저장소 최상위에서 실행하면 v8 rc를 내려받으므로 반드시 `03. 개발`에서 실행한다.
- `npm run dev:test`(3001)는 Next.js 업그레이드 안내로 한 번 멈췄고, 다시 실행해 정상 기동했다. 업그레이드는 하지 않았다.

## 2. Supabase 상태와 일시 정지 방지

### 2-1. 상황

Sol이 Supabase 상태를 물었고, 곧이어 "일시 정지된다는 메일이 왔다"고 알려 왔다. 무료 요금제는 일정 기간 접속이 없으면 프로젝트를 멈춘다. 운영과 시연 DB 둘 다 대상이다.

### 2-2. Sol 결정과 구현

| 항목 | 내용 |
| --- | --- |
| 방식 | **A안: GitHub Actions 정기 실행** |
| 주기 | 사흘마다(cron `0 0 */3 * *`) + 수동 실행 버튼 |
| 동작 | 운영·시연 두 DB에 `psql`로 읽기 전용 조회(`select 'ok '||now()`) 1회 |
| 비밀값 | 저장소 Secrets `SUPABASE_PROD_DB_URL`, `SUPABASE_DEMO_DB_URL` (Sol 등록) |
| 커밋 | main **a753e69** push |

### 2-3. 처리하면서 생긴 문제

| 문제 | 원인 | 조치 |
| --- | --- | --- |
| Actions 탭에 워크플로가 안 보임 | main에 push되기 전이었음 | main에 push |
| 운영 DB 실행 실패 | 비밀번호에 `@`가 있어 접속 주소가 잘못 해석됨 | 워크플로에서 `?쿼리` 제거 후 계정 부분의 `@`를 `%40`으로 바꿔 접속 |

두 DB 모두 수동 실행에 성공했다. 앞으로는 **정지 메일이 다시 오는지만** 지켜보면 된다.

### 2-4. 시연 사이트

Sol이 "시연 사이트는 폐쇄하지 말자"고 정했다. 대화 기록 25의 폐쇄 예정은 취소이고, 계속 운영한다.

## 3. 시험 DB 더미 데이터 등록

대화 기록 25에서 비운 시험 DB에, Sol이 내려받기 폴더에 둔 더미 데이터 문서 세 개를 넣었다. **운영·시연 DB는 건드리지 않았다.**

### 3-1. 화주사

`로지링크_화주사_더미데이터.md` 기준으로 등록했다. 주소는 Sol이 직접 알려 주기로 정했다(권장안). 3·4·5번 주소와 나머지 주소를 Sol이 알려 준 대로 넣었다.

### 3-2. 품목

`로지링크_화주사별_품목_더미데이터.md` 기준으로 한꺼번에 등록했다. 기준 단위가 BOX인 품목 3개에 EA 바코드가 있어 규칙과 부딪쳤는데, Sol이 **EA 바코드만 빼고 등록**(권장안)을 골랐다.

### 3-3. 사용자

`로지링크_화주사별_사용자_더미데이터.md` 기준으로 등록하고, Sol이 붙여 준 5명을 더 넣었다. 바른들식품 아이디는 Sol 지시로 `bd.`가 아니라 **`br.`** 로 바꿨다(변경 이력 남김). 새 사용자는 모두 **마스터 비밀번호**로 맞췄다. 일괄 설정 뒤에 만든 `hf.lee.sol`은 비밀번호가 비어 로그인이 안 됐고, 다시 맞췄다.

### 3-4. 결과 (시험 DB, 11-20 기준)

| 화주사 | 코드 | 품목 | 화주사 사용자 |
| --- | --- | --- | --- |
| 바른들식품(주) | BR01 | **0** | 3 |
| 해담수산 | HD01 | **0** | 2 |
| (주)포근리빙 | PG01 | 20 | 3 |
| (주)모노웍스 | MW01 | 20 | 2 |
| (주)노바기어 | NG01 | 20 | 3 |
| 한결라이프 푸드 | HF01 | 20 | 4 |

3PL 계정 7개는 그대로다. 바른들식품과 해담수산은 **품목 문서에 데이터가 없어서 0건**이다(Sol이 데이터를 주면 추가).

### 3-5. 주의 사항 (시험 DB)

로컬 시험 DB(PGlite)는 **세션이 하나뿐**이다. 확인용 스크립트에서 세션 설정(`SET default_transaction_read_only`)을 한 번 쓰면 그 설정이 남아, 이후 모든 쓰기가 "읽기 전용 트랜잭션" 오류로 막혔다. 설정을 끄고, 앞으로 로컬 DB에는 세션 SET을 쓰지 않기로 메모리에 남겼다.

## 4. 상차 차이 사유 — 차량당 1개에서 품목별로

### 4-1. 문제 제기와 결정 과정

| 순서 | Sol 질문·의견 | 답·결정 |
| --- | --- | --- |
| 1 | 초과·부족은 자동 선택되게 했는데 드롭다운으로 사유를 고르게 돼 있다. 맞는가? | 상태(부족·초과)는 자동, **사유는 사람이 고르는 것**이 맞다고 답함 |
| 2 | 부족과 초과가 한 차량에 같이 있으면 드롭다운 하나로는 못 고른다 | 지적이 맞음. 선택안 제시 |
| 3 | 부족·초과 품목은 사유를 자동으로 채택하면 안 되나? | 상차 사유는 **원인**이라 자동 지정(입고검수 D24 방식)은 맞지 않다고 설명 |
| 4 | **A안: 품목별 사유(권장)로 하자** | 확정 |
| 5 | 좋다, 테스트해 보겠다 | 정의서 v2.0 초안 + 개발 진행 |

### 4-2. 규칙 (정의서 v2.0 ④)

- 차이 품목(부족·초과·지시 외)마다 사유 드롭다운을 둔다. 일치 품목은 사유가 없다.
- 공통코드에 **적용 상태** 속성을 새로 두고, 품목 상태에 맞는 코드만 보이게 한다.
- 차이 품목이 2개 이상이면 **[모든 품목에 같은 사유]** 로 한 번에 채울 수 있다.
- 무지시 상차는 시스템이 모든 품목에 **L04(예정 외 차량)** 를 넣는다.
- 상차를 다시 열었다가 재완료할 때, **이전 사유가 지금 상태에도 맞으면 미리 채운다.**
- v2.0 이전에 저장된 차량 사유는 품목별로 나눠 옮기지 않고 그대로 보여 준다("차량 사유, v2.0 이전").

| 코드 | 이름 | 적용 상태 |
| --- | --- | --- |
| L01·L02·L05 | (기존) | 부족 |
| L03 | (기존) | 부족·초과·지시 외 |
| L04 | 예정 외 차량 | 무지시 전용(시스템 지정) |
| **L06** | 화주사 추가 출고 요청 (신규, 안) | 초과·지시 외 |
| **L07** | ASN 수량·품목 입력 오류 (신규, 안) | 부족·초과·지시 외 |
| L99 | 기타 | 부족·초과·지시 외 (내용 필수) |

L06·L07의 이름과 적용 상태는 **미결 O6**으로 정의서에 남겼다.

### 4-3. 정의서 v2.0 초안

`01. 프로세스/10-입고 업무프로세스 정의서_v2.0.md`를 **새 파일**로 만들었다(v1.9는 그대로). 상태는 '초안, 검토 대기'다.

| 위치 | 바뀐 내용 |

| ⑥ 입고검수 | 상차 차이 사유 참고 표시 |
| C6·D19 | 품목별 사유에 맞춰 수정 |

### 4-4. 구현

| 구분 | 내용 |
| --- | --- |
| DB | `tb_load_d`에 diff_reason_cd·nm·text, `tb_common_code.applies_to`(문자 배열) 추가. L01·L02·L05·L03·L99 적용 상태 채움, L06·L07 추가. 마이그레이션 `20261119000000_load_line_diff_reason` |

`scripts/check-load-rules.ts`도 새 방식에 맞게 고쳤지만, 시드 데이터가 필요해 지금 시험 DB에서는 돌리지 못했다.

### 4-5. 입고검수 참고 표시

Sol이 "입고검수에도 비슷하게 적용할 게 있느냐"고 물었고, 참고 표시를 넣기로 했다. 검수자가 상차 단계에서 이미 알려진 차이를 보고 헷갈리지 않게 하려는 것이다.

| 위치 | 표시 |
| --- | --- |
| 검수 화면 차량 머리 | 상차 차이 요약 |
| 품목 줄 | "상차: {부족·초과·지시 외} · {사유} (ASN x)" |
| 무지시 상차 | "예정 외 차량 · 모든 품목" 한 줄 |
| v2.0 이전 차량 | 차량 사유 한 줄 "(차량 사유)" |
| 확정 뒤 정보 | '상차 차이' 행 |

검수 차이 사유(D24 자동 지정)와는 별개이며 **참고용 표시만** 한다.

## 5. 기타 확인

### 5-1. 입고예정에 기사 정보가 없는 이유

Sol이 포근리빙 계정으로 입고예정을 등록하면서 기사 정보 칸이 없다고 물었다. 물리·논리 분리 원칙상 **입고예정에는 차량·기사가 없고, ASN에서 받는다**고 답했다. Sol이 착각이었다고 확인했다.

### 5-2. 3PL에서 입고예정이 안 보임

Sol이 등록한 입고예정이 3PL에서 안 보인다고 했다. 확인해 보니 **데이터는 정상 저장**돼 있었다. 3PL 사용자는 **자기 센터 입고예정만** 보는데(`src/server/plans/queries.ts` 센터 범위), Sol이 로그인한 han.soyul은 용인1센터 소속이었다.

| 화주사 | 센터 | 상태 | 볼 수 있는 3PL 계정 |
| --- | --- | --- | --- |
| 한결라이프 푸드 | 용인1(YI1) | 승인대기 5 · 승인 5 | han.soyul 등 |
| (주)포근리빙 | 인천3(INC3) | 승인대기 5 | **kim.seojin** |
| (주)노바기어 | 이천2(IC2) | 승인대기 7 | **jung.minseo** |

오류가 아니므로 코드는 바꾸지 않았다.

## 7. 결론

Supabase는 **GitHub Actions로 정지를 막아 두었고**, 시연 사이트는 계속 운영한다. 시험 DB에는 더미 화주사 7곳과 품목 100개, 사용자 19명을 넣어 처음부터 시험할 수 있다. 가장 큰 변경은 **상차 차이 사유를 품목별로 고르게 한 것**으로, 정의서 v2.0 초안과 개발까지 마쳤고 **Sol의 화면 시험과 초안 확인을 기다리는 중**이다. 이 작업은 아직 커밋하지 않았고 마이그레이션도 시험 DB에만 적용했다.
