# 시험 데이터 전 과정(입고예정~입고 완료)·품목 등록 화주사 비우기 대화 요약

## 0. 한눈에 보기

대화 기록 26에 이어서 진행했다. 시험 DB(로컬, 3001)에 **입고예정 등록 → 승인 → ASN → 상차 → 출차 → 입차 → 검수 → 입고 완료**까지 업무 전 과정을 실제 서비스 로직으로 흘려 넣었다. 그 결과 용인1센터 차량 **21대**가 입고 완료되었다. 코드 수정은 **품목 등록 화면에서 이전 화주사가 남아 있던 문제** 1건이다. 이 수정은 아직 커밋하지 않았다.

## 1. 3PL 입고예정 미노출 (설명만)

Sol이 "백소율로 등록한 입고예정이 한소율로 조회하면 안 나온다"고 물었다. 이는 오류가 아니라 정해진 규칙이다. 3PL 사용자는 **자기 센터의 입고예정만** 본다. 한소율은 용인1센터 소속이다. 백소율이 다른 센터로 등록하면 한소율 목록에는 나오지 않는다.

## 2. 품목 등록 화면 화주사 비우기 (코드 수정)

- **증상:** A화주사를 골라 품목 엑셀을 올린 뒤 B화주사 품목을 등록하러 들어가면, 화주사가 A로 선택되어 있었다.
- **원인:** 목록 화면의 화주사 필터가 등록 화면 주소로 넘어갔다.
- **결정(Sol):** "항상 비워 두기". 등록 화면에 들어올 때마다 화주사를 새로 고른다. 다른 화주사 품목으로 잘못 등록하는 것을 막기 위해서다.
- **수정:** `ItemsScreen.tsx`에서 등록 버튼 링크를 `/master/items/new`로 고정하고 `clientQuery`를 제거했다.

### 3-1. 상차 차이 시나리오

차량별로 일치, 부족, 부족+초과, 초과, 0 상차, 지시 외 품목, 기타(L99, 설명 입력)를 돌아가며 넣었다. 사유는 v2.0 규칙대로 품목별로 지정했다(대화 기록 26).

### 3-2. 검수 차이 시나리오

용인1센터 검수자 4명(한소율·이준·박서연·최우진)이 돌아가며, 차량마다 2명이 품목을 나눠 입력했다.

| 검수 전표 | 차량번호 | 검수 차이 |
| --- | --- | --- |
| RC-20261120-0003 | 47다9051 | 훼손 반송 HF01-00013 3개 |
| RC-20261120-0005 | 80마1192 | 부족 NG01-00005 102→91 |
| RC-20261120-0008 | 54더8813 | 품목 불일치 반송 PG01-00019 2개 |
| RC-20261120-0010 | 69아7702 | 초과 HF01-00006 2,882→3,027 |
| RC-20261120-0012 | 57라8130 | 미도착(0) MW01-00007 2,310 |
| RC-20261120-0014 | 16바6645 | 훼손 반송 NG01-00001 1개 |
| RC-20261120-0017 | 45거3402 | 초과 HF01-00008 180→189 |
| RC-20261120-0019 | 94하2943 | 부족 HF01-00001 100→90 |

| 나머지 12건 | — | 차이 없음 |

- 검수 차이 사유는 확정할 때 시스템이 자동으로 지정했다(D24).
- 훼손 반송 건에는 규칙상 사진이 1장 이상 필요해서 **시험용 1×1 그림**을 붙였다. 화면에서는 빈 사진처럼 보일 수 있다.
- 상차 단계에서 0으로 실은 품목은 [남은 라인 전부 0 처리]와 같게 확정했다.

### 3-3. 입고예정 상태 결과

검수 확정과 함께 수량이 입고예정에 자동 배분되었다. 남은 수량이 0이면 **입고완료**, 아니면 **부분입고**가 되었다. 부분입고는 상차 부족·0 상차, 검수 부족·훼손·미도착이 원인이다. 21일 입고예정과 인천2센터·인천3센터 입고예정은 **승인대기로 남아 있다**.

## 5. 결론

시험 DB에 입고예정부터 입고 완료까지 모든 단계의 데이터가 들어갔다. 이제 웹과 PDA의 모든 메뉴를 실제와 비슷한 상태로 확인할 수 있다. 코드 변경은 품목 등록 화면 1건뿐이며 아직 커밋하지 않았다. 다음 순서는 **v2.0 화면 확인 → 정의서 확정 → 커밋 → 운영·시연 반영 시점 결정**이다.
